The intent of this game is to teach language by the natural method. The game in its final form will be much like a text adventure, where the player commands his character in a foreign language with a GUI that allows selecting words, choosing inflections for those words, and dragging words into correct word order. 

This is effectively a text adventure with better graphics. The player character ("PC") opens dialog with a character by saying to himself "I talk to the boy". If it's a valid statement, the player character is then shown approaching the boy, and a dialog opens where the player composes what he says to the boy. The PC might say, "we go north", and if the boy wants friendship or owes the player a favor, he and the player will do that. If the PC says "you go north", then the boy goes north but not the PC. If the PC says "I go north" then the PC goes north but not the boy. The existing GameUpdater and GameState (and possibly some other logic) will be moth-balled into a "explorer" mode that will be analogous to the existing level editor mode, and a new mode will be created whose topmost `*State` object alternates between 1) a state where time is frozen and the dialog box is open and 2) a state where time is moving and the player sees the result of his selection.

The sheer number of possible sentence formations means that translation cannot proceed manually or even by LLM. I also feel that either of these methods will introduce variability that might confuse the player as a language learner. I therefore intend to use a very limited set of words, using scripts from the language-learning folder of this repo that generate text for arbitrary languages:

https://github.com/davidson16807/languages

What is the best way to create this GUI, given the existing libraries we have chosen to work with? 

Keep in mind that the rest of this application uses MVU architecture. In keeping with this, I'd like the GUI to minimize statefulness, and if statefulness is required to work with libraries (chiefly pygame), the GUI logic must be strongly isolated from the rest of the application.

What you store for GUI state will depend on where the player is in selecting dialog so I would start there first. We first need to establish what that dialog looks like. 

The player would start the dialog GUI with a list of lexemes that includes nouns, verbs, and adjectives all together in alphabetical order, which they can drag. Lexemes are indicated to the player using some canonical inflection in the foreign language. Articles and prepositions will be omitted from this list since things like definiteness or position can sometimes be represented by inflection, depending on language.

```
┌ known lexemes ───┐
│ ball             │                                                  
│ boy              │                                                
│ give             │
│ house            │      ┌ inflection grid ────────────────────────┐
│ tall             │      │ the houses   to a house   in the house  │
│ walk             │      │ a house      from the houses   ...      │
└──────────────────┘      └─────────────────────────────────────────┘
┌ playmat ─────────────────────────────────────────────────────────┐
│ [ I ]  [ walk ]  [ to the house ]                        (Speak) │
└──────────────────────────────────────────────────────────────────┘
```

The player can drag entries from lexeme inventories onto a "playmat", for lack of a better word. On the playmat, they can arrange lexemes to reflect desired word order in a sentence. They can also click on lexemes, which presents them with a grid of randomized inflections for that lexeme. The inflection grid opens with the canonical representation selected. The player can collapse the grid using escape or (if trivial to implement) an "x" button, and if the player collapses the grid, it is equivalent to keeping the existing selection. The inflection grid also appears whenever they drag a lexeme onto the playmat. These inflections would be generated by iterating through some dictstore of tagpoints, which would be constructed in some way similar to that shown in inflections_for_*.py files. The player only sees the inflected words in the foreign language - not the lexeme, tagaxes, tags, episemes, etc., and certainly not the English equivalent. Inflection strings would be filtered in the inflection grid that's presented to the player so that duplicates are removed. The inflection is stored as a dictstore. 

Regarding adjectives, the ordering of modifiers like adjectives is itself something a player must learn, so they must be allowed to move adjectives around, but adjectives may intersperse with articles. I propose that inflections for nouns present as a playmat that forms a noun phrase, which come default with articles and adposition where applicable to indicate things like definiteness or position. Adjectives can only be dragged onto noun phrase playmats. 

The strangely merciful thing about all this is that the player can say anything they want within the confines, meaning that we as developers do not need to dig into machine translation until it comes time to generate NPC dialog, and we will never need to dig into natural language processing. After the player confirms his selection by some button at the bottom (depicted as "(Speak)", above), we would simply take the representation of the player's statement from the GUI, which would simply be represented as dictstores containing terms and tokens in English, and verify that term usage is consistent throughout the sentence, and that word order is correct. Since some inflections may be homonymous, inflections would map down to a string representation, and we would check that the inflection that agrees with the rest of the statement has a string that's equivalent to what the player has selected.

If the statement is malformed, the player might be corrected through dialog if possible (e.g. NPC responds "did you say '...'?" then continue as if so) but as an MVP it may simply result in a no-op (e.g. NPC responds "what?" or, if the player is commanding his own character, nothing happens). If the statement is well-formed, the meaning of the statement's representation will be turned into a command, which won't be as difficult as it sounds since possible sentences will be kept remarkably simple (e.g. "I walk to the house", "I give the ball to the boy")

However the path toward NPC dialog will be equally well defined, and will simply amount to using Language.map (under languages.py) to translate list trees to strings of foreign language.

To establish an MVP for this GUI feature, the foreign language will at first simply be English, since it best supports the largest number of words. Once that is established, we will attempt a Spanish version, since of any non-English language, it is most familiar to me.
